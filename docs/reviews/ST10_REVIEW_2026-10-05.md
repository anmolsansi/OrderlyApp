## Finding: P1 — Storage acquisition can crash before recovery runs

Affected examples on the reviewed commit:

- [Account load, line37](https://github.com/anmolsansi/OrderlyApp/blob/64082b2de752302629df215b1e498db4e90f2407/app/account/page.tsx#L37)
- [Profile load, line34](https://github.com/anmolsansi/OrderlyApp/blob/64082b2de752302629df215b1e498db4e90f2407/app/sign-in/page.tsx#L34)
- [Checkout load, lines131–140](https://github.com/anmolsansi/OrderlyApp/blob/64082b2de752302629df215b1e498db4e90f2407/app/checkout/page.tsx#L131)
- [Shared navigation, line16](https://github.com/anmolsansi/OrderlyApp/blob/64082b2de752302629df215b1e498db4e90f2407/app/components/MarketplaceNav.tsx#L16)

The helpers catch exceptions from Storage methods after receiving a Storage object. Browser policies can also throw SecurityError when evaluating window.localStorage itself. Function arguments are evaluated before entering the helper, so its try/catch cannot handle that failure. Shared navigation also reads the property without guarding acquisition. Checkout similarly acquires sessionStorage directly.

Independent Chromium reproduction, using the branch's matching Playwright browser and an init script before page hydration:

```javascript
Object.defineProperty(window, 'localStorage', {
  configurable: true,
  get() { throw new DOMException('ST10 storage getter blocked', 'SecurityError'); }
});
```

Open `/sign-in`, `/account`, and `/checkout` separately. Each emitted an uncaught page error and showed `This page couldn’t load`. Each had zero temporary-profile/continue-without-saving recovery buttons. A control case blocking localStorage.removeItem instead successfully reached Account's temporary profile with no page errors.

The existing [storage E2E case](https://github.com/anmolsansi/OrderlyApp/blob/64082b2de752302629df215b1e498db4e90f2407/e2e/profile-address.spec.ts#L82) blocks removeItem, not acquisition of the Storage object; that narrower test passes.

Required correction: guard acquisition as well as get/set/remove operations; have profile consumers and shared navigation use the safe boundary. Return a typed unavailable result and offer the intended temporary UI. Apply equivalent protection to checkout recovery storage while preserving ST-09's rule that inability to save safe retry state cannot become fake acceptance. Add getter-throwing browser regression tests for these routes; retain existing method-failure tests. This report prescribes behavior, not a particular implementation or new authorization to change source.

## Follow-up — blocker fixed locally, 2026-10-05

User authorized the blocker fix after the original review. Local verification used branch `ST-10-Completed`, base commit `64082b2de752302629df215b1e498db4e90f2407` plus the pending fix. The subsequent publication request is to create a follow-up PR against the existing ST-10 branch and deploy its preview; remote CI and deployment results belong to that PR's exact published head, rather than the original reviewed SHA.

`lib/browser-storage.ts` catches exceptions when acquiring either browser Storage property. Profile/sign-in/account/checkout and shared navigation use it. Profile helpers return typed `storage_unavailable` when no Storage object is available. Checkout recovery helpers never claim that a missing store saved or cleared an idempotency record. If session storage cannot be acquired at load, checkout blocks a new order until the browser setting is corrected and the page reloaded; if it becomes inaccessible just before submit, the recovery write fails before the order API call.

New unit tests cover property acquisition and missing-store result semantics. Five new Chromium tests cover localStorage getter denial on three routes, sessionStorage denial at load, and denial just before submission. The localStorage-denied checkout test completes an actual mock order against isolated FastAPI/Postgres and checks its saved address. The sessionStorage tests assert zero order POST requests. Existing method-level storage failures and lost-response replay remain covered.
