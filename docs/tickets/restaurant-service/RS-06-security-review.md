## Source review (not independent approval)

- Authentication executes before database access and consumes the CON-05 verified subject only. The live route gate defaults to disabled. No guest/demo fallback; synthetic restaurants are excluded.
- Membership queries are tenant-scoped and active-role checks use current PostgreSQL state. The role in the JWT cannot authorize an action. Foreign or absent membership produces the same safe 404. Owner mutations acquire the restaurant lock, then recheck the owner, then lock the target. Last-owner prevention is serialized by the shared parent lock; audit records and membership mutations share one transaction. Tests include two concurrent owners, audit failure rollback and reuse of a revoked identity's valid JWT.
- Exact subject approval is restaurant scoped via `ORDERLY_OPERATOR_VERIFIED_STAFF_SUBJECTS`, a server-controlled JSON object mapping restaurant IDs to exact verified Clerk subjects. No wildcard, user-supplied approval, public enrollment, or runtime provider lookup. Unset/empty denies new enrollment; malformed fails closed. The operator must independently verify subjects before inserting approvals and maintain that list; changing the list alone does not revoke existing membership. Revocation is a membership mutation. Treat this initial-pilot mechanism as an explicit reviewer/owner decision.
- Conformance repair: own-membership list contains only restaurant_id, role, version, not full Membership. Shared fixture and both readers now enforce this. A membership version conflict retains the exact safe COMMON error envelope (409, version_conflict, fields=[expected_version]); clients retrieve current membership through a newly authorized GET and never auto-retry. This is a narrow documented exception to COMMON's current-object-on-conflict statement, proposed for approval. Identical current-version PUT is a no-op with no audit, consistent with CON-06-2. The follow-up tests match actual HTTP responses to shared fixture vectors and prove unauthorized conflict reconciliation cannot read the member. No other provider contract or runtime schema changed.
- Remaining operational risks: the allowlist is persistent server configuration, not provider lifecycle reconciliation. CON-05 still has the documented per-process JWKS availability/rotation tradeoff; protected HTTP error mapping and no protected DB action are covered by RS-06. Neither green CI nor this self-review constitutes independent senior approval.
